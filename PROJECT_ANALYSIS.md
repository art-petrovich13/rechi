# Rechi — анализ проекта и код-ревью

Дата: 06.11.2026. Ветка: `art/flutter` (коммит `7bc743f`).
Анализ отражает состояние до исправлений этапа 0. Что уже исправлено, см. раздел 9.

## 0. Коротко

**Что это.** «Речи» — Telegram Mini App, тренажёр произношения для взрослых
после инсульта и детей с нарушениями речи. Пользователь читает слово, фразу
или предложение вслух, запись оценивает внешний сервис SpeechSuper, приложение
показывает балл по звукам и словам и копит слабые звуки.

**Состояние.** Сделан рабочий демонстрационный MVP. Скелет хороший, сборка и
тесты зелёные. Но ядро продукта — логика тренировки — работает неправильно,
а до production не хватает инфраструктуры и защиты платного API.

**Главные проблемы:**

1. Кнопка «Другое слово» не работает: всегда возвращается то же слово (B1).
2. Упражнение с баллом 5 считается пройденным и больше не появляется (B2).
3. После 43 попыток категория «Слова» заканчивается навсегда: возврата нет,
   «Возвращайтесь завтра» — неправда (B2).
4. Слабый звук нельзя потренировать там, где он нужен больше всего (B3).
5. Прогресс не показывает улучшение: среднее за всё время (B4).
6. Запись, упёршаяся в лимит 20 секунд, почти всегда отклоняется сервером (B5).
7. Соединение с БД занято всё время вызова SpeechSuper (B6).
8. Платный `/assess` ничем не ограничен (S1).
9. Реальные ошибки SpeechSuper не логируются, диагностировать сбои нечем (O1).
10. Качество оценки на реальных пациентах никто не проверял: только TTS и
    взрослый голос. Это главный продуктовый риск (P1).

## 1. Архитектура

### 1.1. Схема

```
Telegram-клиент
   │ /start → кнопка web_app → ${PUBLIC_URL}/app
   ▼
Mini App (Flutter Web, CanvasKit)
   │ HTTPS, Bearer JWT, тот же origin
   ▼
cloudflared / tunnelmole  (временный публичный URL)
   ▼
nginx :8081  ── /app/ → статика mini_app/build/web
   │ /api/, /bot/, /health, /docs
   ▼
FastAPI + aiogram :8000  ──→  SpeechSuper (word.eval.ru / sent.eval.ru)
   │                     ──→  Telegram Bot API (setWebhook, ответы бота)
   ▼
PostgreSQL 16 (users, exercises, attempts)
```

### 1.4. Модель данных

| Таблица | Поля | Заметки |
|---|---|---|
| `users` | `id`, `telegram_id` (unique), `first_name`, `created_at` | только имя из Telegram |
| `exercises` | `id`, `text`, `phonemes` JSONB, `difficulty` 1–3, `category` | `text` без unique |
| `attempts` | `id`, `user_id`, `exercise_id`, `score`, `phoneme_scores` JSONB, `words` JSONB, `created_at` | каскадное удаление с пользователем и упражнением |

`fluency`, `rhythm`, `pronunciation`, `speed`, `duration` в БД **не сохраняются**:
их видно только на экране результата сразу после попытки.

### 1.5. API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/auth/telegram` | `initData` → JWT на 30 дней |
| GET | `/api/v1/exercises/next` | `category`, `focus`, `exclude_id` |
| POST | `/api/v1/assess` | multipart: `audio`, `exercise_id` |
| GET | `/api/v1/history` | последние попытки, `limit` 1–50 |
| GET | `/api/v1/progress` | число попыток и слабые звуки |
| POST | `/bot/webhook` | обновления Telegram |
| GET | `/health` | только факт, что процесс жив |

### 1.6. Основные сценарии

**Вход.** `Telegram.WebApp.initData` → `POST /auth/telegram` → проверка HMAC и
свежести (24 часа) → upsert пользователя → JWT в памяти клиента. На диск токен
не пишется, при каждом открытии вход выполняется заново.

**Выбор упражнения.** Первое упражнение без попыток этого пользователя,
сортировка по `difficulty`, затем `id`. Фильтры: категория и вхождение звука в
`phonemes`. Если ничего нет — 404, клиент показывает «На сегодня всё!».

**Оценка.**
1. Клиент пишет WAV 16 кГц/моно через AudioWorklet (`record_web`) и забирает
   байты из blob URL.
2. `POST /assess`. Сервер читает до 8 МБ, проверяет WAV (0,6–20 с, PCM16) и
   приводит к 16 кГц/моно.
3. Сервер выбирает `word.eval.ru` для одного слова или `sent.eval.ru` для
   фразы, подписывает запрос и ждёт ответ.
4. Парсер приводит фонемы к кириллице: латинские гласные в русские, апостроф
   мягкости убирается, поэтому мягкие и твёрдые согласные сливаются.
   Повторы звука схлопываются **по минимуму**.
5. Попытка сохраняется, аудио нигде не хранится.
6. Клиент показывает `ResultScreen`: «Ещё раз» или «Дальше».

**Прогресс.** Все `phoneme_scores` пользователя грузятся в Python, для каждого
звука считается среднее за всё время, в слабые попадают звуки ниже 70. Порог
проблемного звука в одной попытке другой — 60. Клиент показывает пять худших,
по нажатию открывается тренировка этого звука, всегда в категории «Слова».

**Бот.** Webhook внутри того же процесса FastAPI, команды `/start` и `/help`.
При старте вызывается `setWebhook`.

**Демо-режим.** `MockBackend` внутри `ApiClient` (`MOCK_API=true`, либо debug
без `initData`). В него зашит отдельный набор из 19 упражнений.

## 3. Баги логики и поведения

### Критичные

**B1. «Другое слово» не работает** **[запуск]**
`mini_app/lib/screens/exercise_screen.dart:94` и `:109`

`_loadNext(skip: true)` сначала обнуляет `_exercise` в `setState`, а потом
читает `_exercise?.id`. `setState` выполняется синхронно, поэтому `exclude_id`
всегда `null`. Сервер выбирает детерминированно и возвращает то же упражнение.

Подтверждено дважды: виджет-тестом и в браузере на реальном backend (два
одинаковых `GET /exercises/next?category=word`, на экране снова «РЫБА»). Это
функция из последнего коммита `7bc743f`; бэкенд-часть покрыта тестом, клиентская
нет.

Починка: сохранить id до `setState`.

Даже после этого пропуск будет ходить по кругу: сервер исключает только текущее
упражнение, цепочка получается `рыба → рак → рыба` **[запуск]**. Пропуски надо
помнить на клиенте списком или на сервере. Кроме того, пропуск последнего
упражнения покажет «На сегодня всё», хотя оно осталось.

**B2. Любая попытка навсегда закрывает упражнение** **[запуск]**
`backend/app/exercises/service.py:20-23`

Пройденным считается всё, по чему есть хотя бы одна попытка. Проверено на
реальной БД:

- после попытки с баллом 5 упражнение больше не выдаётся;
- после 43 попыток все «Слова» закончились: `404 All exercises completed`.

Проваленное слово не повторяется, а с баллом 100 считается так же. Экран пишет
«Возвращайтесь завтра — или начните заново с главного экрана», но завтра
упражнений не появится, а кнопки «начать заново» на главной нет. Для
реабилитации, где повторение и есть лечение, это блокер: приложение перестаёт
работать после 90 попыток.

Коммит `dfbfdba` заменил случайную выдачу на последовательную и создал проблему.
Тесты закрепили это как ожидаемое поведение.

Предлагаемая логика (нужно решение, см. раздел 9):
1. Сначала упражнения, которые пора повторить: последний балл низкий, прошло
   время.
2. Затем новые.
3. Затем давно не встречавшиеся.
4. 404 только если контента нет совсем.

Завершённость дня лучше считать отдельно как «дневную норму», а не как
закончившийся контент.

**B3. Фокус на слабый звук ломается, когда он нужнее всего** **[запуск]**
`backend/app/exercises/service.py:23-29`,
`mini_app/lib/screens/home_screen.dart:83-94`

Фокус наследует правило B2. После прохождения слов `focus=Р` даёт 404, хотя
`/progress` в тот же момент показывает Р с баллом 5. Экран при этом пишет
«Нет упражнений со звуком Р», что неверно: их 12, они просто «пройдены».

Фокус всегда запускается с `category=word`, упражнения со звуком в
словосочетаниях и предложениях не используются. Покрытие слов очень неравномерно:

| Упражнений со звуком в словах | Звуки |
|---|---|
| 0 | Э |
| 1 | В, Ф, Х, Г |
| 2 | Д, Щ, Н |
| 3–5 | Т, Ж, З, И, Ч, Й, С, П, Ц |

**B4. Прогресс не показывает прогресса** **[запуск]**
`backend/app/progress/service.py:27-47`

Среднее за всё время без окна и веса. 20 старых попыток по 30 баллов плюс 10
свежих по 95 дают 52, звук остаётся «слабым», хотя человек уже говорит хорошо.
Цель продукта — видеть динамику, а она не видна. Нет графиков, сравнения недель,
серий занятий.

Дополнительно усиливает эффект **агрегация по минимуму**
(`speechsuper/parser.py:66-72`): звук Р с баллами 95 и 40 в одной фразе
сохраняется как 40. Фразы и предложения систематически занижают звуки.

Плюс каждое обращение грузит все попытки пользователя в Python.

**B5. Запись на лимите 20 секунд отклоняется** **[запуск: сервер; код: клиент]**
`mini_app/lib/screens/exercise_screen.dart:215`,
`backend/app/assessment/audio/validator.py:53`

Клиент останавливает запись, когда `elapsed >= 20 с`, таймер тикает раз в 100 мс,
потом ещё задержка на `stop()`. Сервер отклоняет всё больше 20,0 с: 20,01 с уже
даёт 400. AudioWorklet может отбросить неполный буфер (до ~43 мс при 48 кГц), но
этого обычно мало. В итоге автоостановка почти всегда приводит к ошибке, а
пользователь видит общее «Не удалось выполнить запрос. Попробуйте ещё раз»
(см. B8). Пострадают те, кто говорит медленно, то есть целевая аудитория.

Починка: останавливать на ~19,5 с и/или допускать на сервере запас до 21 с.

**B6. Соединение с БД занято на всё время вызова SpeechSuper** **[запуск]**
`backend/app/assessment/service.py:25-45`, `app/api/dependencies/auth.py:30`

`db.get()` открывает транзакцию, она висит до `commit()` после ответа внешнего
сервиса. На 20 параллельных `/assess` с задержкой 2 с в `pg_stat_activity` было
**15 соединений `idle in transaction`** — весь пул (5 + 10). Остальные запросы
встали в очередь: `/progress` занял 1,31 с вместо миллисекунд, 20 запросов
выполнились за 4,2 с вместо 2 с. При таймауте 30 с и всплеске нагрузки запросы
начнут падать по `pool_timeout`.

Починка: прочитать упражнение, завершить транзакцию, вызвать SpeechSuper, потом
короткой транзакцией сохранить попытку.

### Высокие

**B7. Фонемы упражнений и фонемы SpeechSuper — разные словари** **[запуск/код]**
`backend/seed.py`, `speechsuper/parser.py`

Контракт обещает, что ключи `phoneme_scores` совпадают с `phonemes` упражнения.
На деле seed смешивает буквы и звуки:

- 40 из 90 упражнений содержат Я, Ю, Ё или Ь. По реальному ответу в контракте
  «я» приходит как `Й, А`, значит такие ключи не совпадут и фокус по ним мимо.
- Транскрипция непоследовательна: `ёж` → Й О Ш (фонетика), `яблоко` → Я Б Л О К
  (буквы), `мяч` → М А Ч, `цапля` → Ц А П Л Я, `цыплёнок` содержит и Ё, и О.
- «маленький котёнок пьёт молоко» содержит звук **Д**, которого в тексте нет.
- 7 фраз и предложений не содержат часть своих букв («дети рисуют дом и солнце»
  без Л, «бабушка вяжет тёплый шарф» без У).
- 4 слова (шапка, лампа, чашка, ракета) содержат дубли, контракт требует
  уникальности.

Следствие: фокус находит случайный набор, чипы до и после записи не совпадают,
статистика по Я/Ю/Ё не связана с реальностью.

Починка: генерировать транскрипцию одним алгоритмом и валидировать тестом. Лучше
всего — собрать фактические фонемы из ответов SpeechSuper и сверить.

**B8. Пользователь не видит причину отказа** **[код]**
`mini_app/lib/core/api_client.dart:239-258`

Любой 400 показывается как «Не удалось выполнить запрос». Клиент не отличает
слишком длинную запись, битый файл и отказ SpeechSuper (тишина, шум), хотя
причина приходит в `detail`. Нужны коды ошибок в API и свои тексты: человек
должен понимать, что сделать иначе.

Также 502/503/504 везде называются «Сервис анализа речи недоступен», даже на
экранах истории и прогресса, где он ни при чём.

**B9. Любой `warning` от SpeechSuper отменяет попытку** **[проверить]**
`speechsuper/parser.py:40-47`

Если предупреждение не критичное (например, тихий голос), человек получает
отказ вместо оценки. Тихая речь типична для целевой аудитории. Нужно уточнить в
документации SpeechSuper, какие коды реально означают брак записи.

**B10. Метрики темпа теряются** **[код]**
`assessment/service.py:30-43`

`fluency`, `rhythm`, `pronunciation` не пишутся в `attempts`. Для восстановления
речи темп и ритм — главные показатели, а динамику построить не из чего, и
накопленные данные уже потеряны. Простое и дешёвое изменение схемы, лучше
сделать раньше.

### Средние

**B11. Алиасинг при ресемплинге** **[запуск]**
`assessment/audio/validator.py:88-108`

`audioop.ratecv` — линейная интерполяция без фильтра. Тон 12 кГц при 48 кГц
после понижения до 16 кГц не исчез, а стал тоном 4 кГц той же амплитуды.
Свистящие (С, Ш, Щ), которые приложение и тренирует, живут именно в этой полосе.
Работает только если пришло не 16 кГц: `record_web` 2.1.3 по коду ресемплит сам,
но коммит `831ba0c` говорит о реальных 48 кГц с телефонов. Нужно выяснить, что
приходит с iPhone и какого качества ресемплер в worklet **[проверить]**.
Кроме того, `audioop` удалён из Python 3.13, это блокирует обновление
интерпретатора.

**B12. Значение Infinity в ответе даёт 500** **[запуск]**
`speechsuper/parser.py:177`. `round(float('inf'))` бросает `OverflowError`,
а ловятся только `TypeError` и `ValueError`. Маловероятно, но 500 вместо 502.

**B13. Падение Telegram роняет весь API** **[код]**
`backend/app/bot/lifecycle.py:47-49`. Ошибка `setWebhook` при старте пробрасывается,
процесс не запускается, контейнер уходит в перезапуск. Если сервер не достучится
до `api.telegram.org`, тренажёр будет недоступен целиком, хотя ему бот не нужен.

**B14. Дубликаты при повторе после таймаута** **[код]**
Клиент ждёт 60 с, повтор создаёт новую попытку, даже если первая уже сохранена.
Заодно это второй платный вызов. Нужен ключ идемпотентности.

**B15. Гонки в экране упражнения** **[код]**
`exercise_screen.dart`. Пока `await _recorder.stop()` не завершился, кнопка
записи снова активна: `_recording` уже `false`, а `_starting` тоже. Быстрый тап
запустит новую запись, а потом старый результат перезапишет состояние.
Быстрые нажатия «Другое слово» могут привести ответы в другом порядке.

**B16. Минимальная длительность проверяется по таймеру** **[код]**
Клиент сравнивает с 0,6 с время по таймеру, а не длину аудио, поэтому запись около
этой границы может пройти клиент и получить отказ на сервере.

## 4. Безопасность и приватность

**S1. У `/assess` нет лимитов** (высокий) **[код]**
Каждый вызов — платный запрос. Пользователь или скрипт может сжечь бюджет. Нужны
лимиты на пользователя (в минуту и в день) и глобальный, плюс алерт по расходу.
Также запись из тишины отправляется в SpeechSuper: проверка энергии сигнала на
сервере сэкономит кредиты.

**S2. Секрет webhook необязателен и не задан** (высокий) **[код]**
`bot/webhook.py:44-55`. В локальном `.env` `TELEGRAM_WEBHOOK_SECRET` пуст, в
`WINDOWS_SETUP.md` он не упомянут. Любой, кто знает URL, может слать боту
поддельные обновления. Секрет должен быть обязательным при включённом боте.

**S3. Уязвимые зависимости** (высокий) **[запуск: OSV]**
- `python-jose 3.3.0`: CVE-2024-33663, CVE-2024-33664, CVE-2024-29370. Проект
  использует HS256 с явным списком алгоритмов, поэтому подмена алгоритма напрямую
  не применима. Минимум обновить, лучше перейти на PyJWT.
- `starlette 0.46.2` (ставится транзитивно через fastapi 0.115): ряд CVE 2025–2026,
  в том числе DoS при разборе больших форм и подмена Host. Часть не применима (мы
  не используем `StaticFiles`). Нужно обновить FastAPI.
- `requirements.txt` с масками `==0.115.*` и без lock-файла: сборки не
  воспроизводимы.

**S4. Обещание «Аудио не сохраняется» неполное** (высокий) **[проверить]**
`exercise_screen.dart:583`, `how_it_works_sheet.dart`. Голос уходит третьей
стороне. Что SpeechSuper хранит и где, я подтвердить не смог. Для детей и
пациентов это чувствительные данные, а голос и сведения о нарушениях речи могут
подпадать под особые категории персональных данных.

Нет согласия на обработку, политики, удаления данных (контракт сам это признаёт),
согласия родителей для детей. Нужно обсудить с юристом до реальных пользователей,
а текст в интерфейсе заменить на точный.

**S5. Порт API открыт наружу** (средний) **[код]**
`compose.yaml`: `"8001:8000"` слушает все интерфейсы, а `WINDOWS_SETUP.md`
утверждает, что API доступен только через nginx. Нужно `127.0.0.1:8001:8000` или
убрать порт.

**S6. Swagger опубликован в production** (средний) **[код]**
`/docs` и `/openapi.json` проброшены в nginx. Лучше отключать вне debug.

**S7. Некорректная конфигурация обнаруживается поздно** (средний) **[код]**
Пустой `JWT_SECRET` или `BOT_TOKEN` не мешает старту, но каждый запрос даёт 500.
Нужна проверка при запуске. Пустые `SPEECH_SUPER_*` дают 502 тоже только во время
работы.

**S8. Прочее** (низкий) **[код]**
- контейнер работает от root;
- пароль Postgres `postgres` прямо в `compose.yaml`;
- нет отзыва JWT, срок 30 дней;
- инструкция предлагает переносить секреты в zip;
- `age < 0` в проверке `auth_date` даёт отказ при расхождении часов на секунду.

## 5. Инфраструктура и эксплуатация

**O1. Ошибки SpeechSuper не логируются** (высокий) **[запуск]**
`api/v1/assessment.py:83-87` глотает `SpeechSuperError` без записи в лог.
Закончились кредиты, неверный ключ, таймаут — снаружи одинаковый 502, причина
теряется. Логирование не настроено вообще: уровень INFO для `app.*` отключён, что
проверено под uvicorn. Поэтому строка `Telegram webhook registered`, которую
`WINDOWS_SETUP.md` просит найти в логах, **никогда не появится**.

Нужны: структурные логи, request id, Sentry или аналог, счётчики длительности и
ошибок SpeechSuper.

**O2. Схема БД расходится с моделями** (высокий) **[запуск]**
`alembic check` падает: индекс `ix_exercises_category` есть только в миграции,
`telegram_id` описан по-разному (отдельный unique и неуникальный индекс против
уникального индекса). Следующий `--autogenerate` предложит удалить индекс. В
тестах это не отслеживается.

**O3. Развёртывание рассчитано на демо** (высокий) **[код]**
Один ПК с Windows и временный туннель: URL меняется, нужно править `.env` и
пересоздавать контейнер. Нет постоянного домена, бэкапов БД, мониторинга.

**O4. Нет сжатия и кэширования в nginx** (высокий) **[код + проверить]**
В `deploy/nginx.conf` нет `gzip` и заголовков кэша. Первая загрузка в браузере
на базе Chromium: `main.dart.js` 2,43 МБ + `canvaskit.wasm` 5,43 МБ = 7,9 МБ без
сжатия против 2,8 МБ с gzip. Для мобильной сети и пожилого пользователя это
десятки секунд на белом экране. `index.html` без `no-cache` может застревать в
WebView после обновления. Проверить `curl -H 'Accept-Encoding: gzip'`.

**O5. `telegram-web-app.js` блокирует загрузку** (средний) **[проверить]**
`web/index.html:26`. Синхронный скрипт стоит в `<head>` до splash. Если
`telegram.org` недоступен с устройства, страница висит пустой до таймаута, а потом
приложение покажет «Откройте через Telegram». Рассмотреть локальную копию или
неблокирующую загрузку.

**O6. Нет CI** (средний). Тесты, анализатор, `alembic check`, валидация контента
должны запускаться на каждый PR.

**O7. nginx может потерять API после пересоздания контейнера** (средний)
**[проверить]**. `proxy_pass http://api:8000` резолвится при старте nginx, а
документированный сценарий смены туннеля пересоздаёт только `api`.

**O8. Контент зашит в код** (средний) **[код]**
`seed.py` запускается при каждом старте, строки только добавляет и обновляет.
Удалённое из списка останется в БД и в выдаче, переименование создаст дубль.
`text` без unique. 90 упражнений живут отдельно от 19 в моке. Каскад
`exercises → attempts` при удалении упражнения стирает историю пользователей.
Нужны стабильные ключи, soft delete и единый источник контента.

**O9. Мелочи** **[код]**
- `/health` не проверяет БД;
- `rechi-web-build.zip` (14 МБ) скрыт только локально через `.git/info/exclude`,
  корневого `.gitignore` нет, на чужой машине попадёт в коммит;
- 15 с `SPEECH_SUPER_TIMEOUT_SECONDS` по умолчанию мало для 20-секундной записи;
- новый `httpx.AsyncClient` на каждый запрос означает новый TLS к SpeechSuper;
- CORS не настроен: это правильно при одном origin, но README описывает запуск
  `flutter run` против API, который не заработает.

## 6. UX и продукт

**P1. Точность оценки на реальных пациентах не подтверждена** (критичный)
Сами документы говорят о проверке на TTS и взрослой речи, задача «проверить на
живой детской и взрослой речи» открыта с 24.10. SpeechSuper, насколько мне известно,
рассчитан на оценку обычного произношения, а не дизартрии, афазии и детской речи. Оценка может быть
несправедливо низкой и демотивировать человека либо завышенной и закреплять
ошибки. Без пилота с логопедом непонятно, работает ли продукт. Сделать это нужно
раньше новых функций.

**P2. Нельзя услышать эталон и себя** (высокий)
Нет озвучки образца и прослушивания своей записи. Для логопедической работы
«услышать → повторить → сравнить» это основа. Людям с алексией и маленьким детям
иначе задание недоступно вовсе: приложение требует уметь читать.

**P3. Кнопка записи недоступна для скринридера** (высокий) **[запуск]**
`widgets/record_button.dart:87-91`, `phoneme_chip.dart:88-98`.
`Semantics(button: true)` плюс `ExcludeSemantics` без `onTap`: виджет-тест показал
отсутствие tap-действия и у записи, и у слабых звуков. Человек со скринридером
слышит кнопку, но нажать её не может. На Flutter Web семантика к тому же включается
только по запросу.

**P4. Telegram-интеграция минимальная** (высокий) **[код]**
- нет `disableVerticalSwipes`: длинные экраны прокручиваются жестом, который может
  сворачивать Mini App, а на главной ещё и pull-to-refresh;
- нет Telegram `BackButton`, используется только своя стрелка;
- нет подтверждения закрытия при записи и отправке.

**P5. Нет понятия занятия** (высокий)
Написано «3–5 минут в день», но нет дневного плана, цели, завершения, серии дней,
напоминаний от бота (сейчас бот только показывает кнопку). Для регулярности
реабилитации это главный рычаг удержания.

**P6. Сложность не отражает сложность** (средний)
Первое же задание — «рыба», «рак», «роза»: Р один из самых трудных звуков, а стоит
на уровне 1. Уровни не связаны с артикуляцией. Нужен методически выстроенный
порядок от логопеда.

**P7. Смешанный тон** (средний)
«Твой прогресс», «Попробуй», «Подними кончик языка» рядом с «Нажмите», «Готовы
потренировать речь?». К взрослому пациенту на «ты», к ребёнку слишком сухо.
Советы по артикуляции написаны без проверки специалистом. Нет разделения аудитории.

**P8. Мягкие и твёрдые согласные объединены** (средний)
Парсер убирает мягкость: Р и Рь идут как один звук, хотя в логопедии это разные
цели. Текущая модель такое различить не может.

**P9. Текст ограничен масштабом** (низкий) **[код]**
Масштаб шрифта обрезан на 1,3, для слабовидящих мало. `RecordButton` содержит
дублирующие обработчики нажатия. На экране результата много карточек мелким
текстом для пожилых пользователей.

**P10. Интерфейс выглядит аккуратно.** На 375×812 Home, онбординг и экран
упражнения отображаются корректно, консольных ошибок нет. Вход, загрузка прогресса
и упражнения проходят на реальном backend. Запись микрофоном не проверялась.

## 7. Качество кода

### Тесты

- **Тесты бэкенда почти не проверяют поведение.** БД заменена на `MagicMock`, а SQL
  проверяется поиском подстроки: `assertIn("NOT IN", statement)`. Поэтому B2, B3 и
  B6 тесты не видят, а поведение B2 ими закреплено.
- **На клиенте нет тестов экранов.** `widget_test.dart` проверяет только чипы и
  бейдж, поэтому B1 прошёл незамеченным при 40 зелёных тестах.
- **Не хватает:** интеграционных тестов на Postgres, валидации seed, проверки
  границ аудио, тестов `ExerciseScreen`.
- Зависимостей для тестов нет в отдельном файле, версия Python нигде не закреплена
  кроме Dockerfile. На этой машине только 3.9 — проект не запустится без отдельной
  установки.

### Backend

- HTTP-логика протекла в роутер: сборка DTO, разбор JSON прямо в `history.py`.
- `problematic_phonemes` импортируется из `assessment` в роутер истории.
- Пороги 60 и 70 рассыпаны по разным модулям и продублированы в клиенте.
- `api/v1/exercises.py` возвращает 404 с одним текстом и для «контента нет», и для
  «всё пройдено»: клиент не может их различить.
- `ExerciseCategory(item.category)` даст 500 на неожиданном значении: у колонки нет
  CHECK.

### Клиент

- `exercise_screen.dart` — 1019 строк, около 18 полей состояния и смесь записи,
  сети, навигации, таймеров и вёрстки. Отсюда B1 и B15. Нужен контроллер с явной
  машиной состояний: `idle → recording → recorded → sending → result`.
- `Assessment.fromJson` дублирует `readWordAssessments`.
- Карточка с тенью скопирована минимум 4 раза, стоит вынести `AppCard`.
- Неиспользуемый код: `readDouble`, `kindLabel`, `isServiceUnavailable`,
  `Progress.empty`, `ProgressService.reset`.
- `cupertino_icons` в зависимостях не используется, но шрифт грузится при старте
  (виден в сети).
- Комментарии в `ApiClient` и `AuthResponse` ссылаются на `/api/...` без `v1`.
- В `mock_backend.dart:383-384` дублируется строка документации.
- `readInt` молча превращает мусор в 0: балл 0 неотличим от сбоя данных.
- `AuthResponse` подставляет `User(id: 0)`, если сервер не вернул пользователя.
